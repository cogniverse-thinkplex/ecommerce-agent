# 单机生产基线设计

## 目标

把当前“本地可完整演示”的电商 Agent 提升为可在一台受控服务器上稳定部署、监控、备份和恢复的准生产版本。生产启动必须尽早拒绝危险配置；运维人员能够区分进程存活与依赖就绪；HTTP 请求可通过请求 ID 和结构化日志追踪；SQLite 数据可在线一致备份并经过恢复校验。

## 范围

- 保留 FastAPI、SQLite、tau2-retail MCP 和现有前端，不改写业务架构。
- 新增仅在 `ECOM_ENV=production` 生效的配置门禁，本地开发与测试保持兼容。
- `/health` 仅表示进程存活；`/ready` 验证 SQLite 与工具后端可用性。
- 所有响应携带安全头与请求 ID；请求结束输出不包含正文、Cookie 或密钥的 JSON 日志。
- 使用 SQLite backup API 在线备份，备份与恢复前后执行 `integrity_check`，恢复覆盖必须显式指定。
- 提供生产 Compose 覆盖配置、无秘密的环境模板和操作手册。

## 非目标

- 本阶段不引入 PostgreSQL、Redis、消息队列、Kubernetes 或多副本。
- 不承诺 SQLite 的跨节点高可用；单机故障通过备份恢复处理。
- 不在仓库中保存 API Key、生产数据库或真实客户数据。

## 方案选择

考虑过三种方案：直接延用当前 Compose（成本最低但缺少故障隔离与恢复能力）；立即迁移 PostgreSQL/Redis（扩展性最好但会显著扩大迁移风险）；在现有架构上建立单机生产基线。选择第三种，因为它能在不扰动已完成业务闭环的前提下解决当前最现实的运行风险，并为后续横向扩展保留边界。

## 关键行为

1. 生产配置要求 SQLite 绝对路径、MCP 工具后端、LLM planner、安全 Cookie、离线策略向量模型和对应模型供应商密钥。错误信息只列变量名和修复方法，不回显值。
2. 存活探针不访问外部依赖；就绪探针检查数据库 `SELECT 1`/迁移表和工具目录，失败返回 HTTP 503 及逐项状态。
3. 客户提供的请求 ID 只有匹配 `[A-Za-z0-9._-]{1,128}` 才被采用，否则生成 UUID。日志仅记录方法、路由、状态码、耗时和请求 ID。
4. 安全头默认在所有响应生效；HSTS 仅生产环境开启。CSP 兼容当前静态页面的内联样式，但禁止第三方脚本、对象和 iframe 嵌入。
5. 备份写入临时文件，校验成功后原子改名；元数据记录源、时间、大小和 SHA-256。恢复默认拒绝覆盖，`--replace` 时先创建安全副本。

## 验收

- 新增单元/API/运维配置测试均通过，完整后端回归无失败。
- 生产配置缺项时应用启动失败，错误不包含秘密。
- `/health` 与 `/ready` 的语义和状态码可由自动化测试证明。
- 能对临时 SQLite 数据库完成备份、完整性检查、恢复和内容比对。
- Docker Compose 配置可解析，API 健康检查改用 `/ready`，服务具备重启、资源和日志轮转约束。
