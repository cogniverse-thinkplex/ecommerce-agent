# Agent 驱动的订单中心设计

## 意图

为已登录客户提供独立订单中心，让明确的信息查询保持快速、可靠，同时让 Agent 负责模糊意图、多步骤售后、跨订单处理、政策判断和写操作确认。订单中心不是另一套订单业务系统，也不能绕过现有 Agent、MCP、Policy Guard 与 fingerprint confirmation。

## 目标

- 客户可以查看只属于自己的订单列表和完整订单详情。
- 客户可以按全部、待处理、已发货、已送达、已取消筛选订单。
- 订单详情展示商品、金额、支付记录、配送地址和当前状态。
- 桌面端提供右侧上下文 Agent 助手；移动端使用可展开的底部助手面板。
- 从订单发起咨询或售后时，页面把订单 ID 作为受信任的结构化上下文绑定到新会话或当前会话。
- 所有写操作仍由 Agent 生成提案，经过工具校验、Guard、精确参数确认和 MCP 执行。

## 非目标

- 不在订单 API 中新增取消、退货、换货等直接写接口。
- 不让前端决定订单是否符合售后政策。
- 不在首版增加真实物流供应商、电子发票或再次购买。
- 不允许客户端提交任意 `user_id` 或读取其他客户订单。

## 采用方案

采用“查询中心 + 上下文 Agent 助手”。相比纯查询页面，它保留复杂任务中的 Agent 价值；相比直接自助写 API，它不会复制确认、政策和审计规则。

## 页面结构

新增 `/orders/`，沿用当前客户产品的白色、墨色、珊瑚红与绿色视觉体系。

### 顶部导航

统一客户侧一级导航：`客服`、`订单`、`消费分析`、`账户`。客服中心侧栏增加“我的订单”，账户和消费分析页面也增加订单入口。

### 订单区域

- 页面标题、订单总数和状态筛选 tabs。
- 订单列表使用紧凑行式布局，不使用嵌套卡片。
- 每项显示订单号、演示购买日期、状态、商品摘要、支付净额。
- 选择订单后显示详情；桌面端列表和详情并列，移动端进入详情视图后可返回。
- 空状态、加载状态和失败重试必须完整。

### Agent 助手

- 桌面端位于订单详情右侧，移动端为底部抽屉。
- 初始状态显示当前订单号和符合语境的建议问题，但不声称订单一定具备某种资格。
- 用户可以输入自然语言，也可以点击“查询进度”“申请取消”“申请退货或换货”等快捷入口。
- 助手复用现有客服会话、SSE、业务卡片和 confirmation 交互，不实现第二套聊天协议。
- 页面传入 `order_context={order_id}`，服务端验证该订单确实属于当前登录客户，再把它写入 Agent 的 `active_order_id`；不得信任前端提供的状态、金额或商品。
- 订单上下文只影响当前会话。用户明确提及其他订单时，Agent 仍可按已有权限规则切换。

## 后端设计

### `OrderCenterService`

新增 `backend/app/orders/service.py`：

- 从 `AuthenticatedUser.retail_user_id` 调用 `get_user_details` 获取订单 ID。
- 对每个订单调用 `get_order_details`；任何订单都必须再次验证属于该客户的可信订单集合。
- 复用 `demo_order_metadata` 提供演示购买日期。
- 计算支付金额、退款金额和净额时使用与消费分析一致的口径。
- 将工具错误归一化为客户可理解且不泄露内部信息的错误。

### API

- `GET /api/v1/orders?status=...`：返回当前客户的订单摘要。
- `GET /api/v1/orders/{order_id}`：返回本人订单详情；非本人和不存在统一返回 404。
- `POST /api/v1/support/conversations/{conversation_id}/order-context`：验证归属后设置当前会话 `active_order_id`，并记录 `conversation.order_context_set` 事件。

订单响应采用显式 Pydantic 模型，不直接透传 tau2 字典。支付方式需脱敏；不返回用户 ID、内部数据库字段或原始工具错误。

## 权限与一致性

- API 只从 HttpOnly Session 获取客户身份。
- 开发人员不能通过订单中心读取客户订单，继续跳转工程控制台。
- 列表与详情不接受 `user_id`。
- 上下文绑定必须同时校验会话归属和订单归属。
- 页面快捷按钮只发送自然语言意图，不调用写工具。
- 所有写操作继续走 `LLMProposalGenerator -> Skill -> proposal validation -> Guard -> confirmation -> MCP`。

## 状态与失败处理

- 列表允许部分成功：单个订单详情不可用时返回该订单的安全占位状态，并允许重试。
- Agent 面板与订单数据读取分离；聊天暂时不可用不影响查看订单。
- SSE 断线继续使用现有安全回退和错误收集。
- 页面刷新后恢复当前 URL 中的订单选择，但不把订单内容存入浏览器 storage。

## 可观测性

- 订单读取记录 API 延迟和工具失败，但不计入 Agent 成功率。
- 上下文绑定记录会话、订单 ID 和时间，不记录敏感支付内容。
- 通过订单中心发起的 Agent 运行增加安全来源标签 `order_center`，便于质量控制台比较入口效果。

## 测试与验收

- 单元测试：金额口径、状态筛选、订单所有权、部分失败。
- API 测试：未登录、开发人员、本人订单、跨账户订单、无效状态。
- Agent 测试：上下文绑定设置 `active_order_id`，不能绑定他人订单，写操作仍等待确认。
- 静态测试：导航、筛选、空状态、助手面板和无内部术语。
- 浏览器测试：桌面与 390px 移动端，无横向溢出；从订单打开助手、发送问题、收到流式响应、写操作出现确认卡。
- 完整回归测试必须继续通过。

## 后续扩展

购物政策与帮助中心完成后，助手回答资格问题时引用具体政策条款。未来可增加真实物流时间线、电子收据、再次购买和售后工单状态，但仍保持查询页面与 Agent 写操作边界。
