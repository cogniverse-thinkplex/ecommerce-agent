# Authentication and Role Routing Design

**Date:** 2026-10-21

## 1. Goal

Add persistent local authentication and role-based access control to the existing e-commerce agent product. A normal customer signs in and uses the Chinese support center. A developer signs in and uses the existing engineering Dashboard, including its observation, trace, audit, evaluation, cost, task, and testing capabilities. The Dashboard also gains developer-account administration.

This milestone remains a local quasi-product. It does not attempt enterprise SSO, multi-tenant administration, password recovery by email, or production identity verification.

## 2. User Experience

### 2.1 Public pages

- `/login/` is the single login page for both roles.
- `/register/` creates customer accounts only.
- `/health` and the static assets needed by login and registration remain public.
- `/` resolves the current session and redirects developers to `/dashboard/`, customers to `/support/`, and unauthenticated visitors to `/login/`.

### 2.2 Customer experience

- A customer login redirects to `/support/`.
- Customers can create, list, read, archive, and operate only conversations they own.
- Customers cannot open `/dashboard/` or call engineering, evaluation, trace, policy, reset, or developer-management APIs.
- The retail agent still performs its existing domain identity verification before disclosing retail data. Product-account login and retail-domain authentication are separate controls.

### 2.3 Developer experience

- A developer login redirects directly to the existing `/dashboard/`.
- The current Dashboard remains the complete developer observation page; no second administration application is introduced.
- Existing Dashboard tabs and engineering APIs remain available to authenticated developers.
- A new `开发人员管理` tab lists developer accounts and creates, enables, or disables them.
- Developers may open `/support/` for product testing, but this does not grant ownership of another customer's conversations.

### 2.4 First login

Migration data creates one initial developer:

- Email: `admin@local.dev`
- Temporary password: `Admin@123456`
- Role: `developer`
- `must_change_password`: true

The password is represented in migration seed data as a precomputed salted hash, never plaintext. The plaintext value exists only in documentation. The initial developer must change the password before accessing either product surface or privileged API.

## 3. Data Model

Migration `002_authentication.sql` adds the following structures.

### 3.1 `users`

| Column | Type | Constraints | Purpose |
| --- | --- | --- | --- |
| `user_id` | TEXT | PK | UUID generated by the application; stable seed ID for initial admin |
| `email` | TEXT | NOT NULL, unique normalized index | Login identifier stored lowercase and trimmed |
| `display_name` | TEXT | NOT NULL | User-facing name |
| `password_hash` | TEXT | NOT NULL | Versioned scrypt encoding containing parameters, salt, and digest |
| `role` | TEXT | CHECK customer/developer | Authorization role |
| `status` | TEXT | CHECK active/disabled | Login eligibility |
| `must_change_password` | INTEGER | CHECK 0/1 | Blocks normal application access until changed |
| `created_by_user_id` | TEXT | nullable FK users | Developer creator; null for public customer registration and seed |
| `created_at` | TEXT | NOT NULL | UTC ISO timestamp |
| `updated_at` | TEXT | NOT NULL | UTC ISO timestamp |
| `last_login_at` | TEXT | nullable | Successful login timestamp |

Email uniqueness is case-insensitive through a normalized unique index. Disabled accounts cannot create new sessions; disabling an account revokes its existing sessions in the same transaction.

### 3.2 `auth_sessions`

| Column | Type | Constraints | Purpose |
| --- | --- | --- | --- |
| `session_id` | TEXT | PK | Internal UUID |
| `user_id` | TEXT | NOT NULL FK users | Session owner |
| `token_hash` | TEXT | NOT NULL UNIQUE | SHA-256 hash of a 256-bit random browser token |
| `created_at` | TEXT | NOT NULL | UTC ISO timestamp |
| `expires_at` | TEXT | NOT NULL | Absolute expiration |
| `last_seen_at` | TEXT | NOT NULL | Last validated use |
| `revoked_at` | TEXT | nullable | Explicit logout, password change, or account disable |

Raw session tokens are returned only in an `HttpOnly` cookie and are never persisted. Sessions expire after 12 hours by default. Password changes revoke every prior session and create one replacement session.

### 3.3 `auth_audit_events`

Records login success/failure, registration, logout, password change, developer creation, and account status changes. Payloads may contain user IDs and normalized email but never passwords, hashes, raw cookies, or API keys.

### 3.4 Conversation ownership

Add nullable `owner_user_id` to `conversations` with a foreign key to `users` and an owner/update index.

- New support conversations always receive the authenticated customer's user ID.
- Customer queries always include `owner_user_id = current_user.user_id`.
- Existing unowned conversations remain readable from developer engineering tools but are not exposed through customer support APIs.
- Archiving is authorization-aware and remains a soft delete.

## 4. Password and Session Security

Use Python standard-library `hashlib.scrypt` with a random 16-byte salt, constant-time verification through `hmac.compare_digest`, and a versioned string format. Registration and password changes enforce at least 12 characters containing upper case, lower case, a digit, and a non-alphanumeric character.

The browser cookie is named `ecom_session`, has `HttpOnly`, `SameSite=Lax`, `Path=/`, and configurable `Secure`. The default local HTTP setup uses `Secure=false`; container or reverse-proxy deployment must enable it.

Authentication errors use a single Chinese invalid-credentials response so email enumeration is not exposed. Login attempts are audited. This local milestone does not implement distributed rate limiting; the remaining production gap documents that limitation.

## 5. Application Boundaries

### 5.1 Authentication service

Create an `AuthService` above repository protocols. It owns registration, authentication, password changes, session creation/revocation, role checks, developer creation, and developer status changes. Routers do not issue SQL.

### 5.2 API routes

Public/session routes under `/api/v1/auth`:

- `POST /register`
- `POST /login`
- `POST /logout`
- `GET /me`
- `POST /change-password`

Developer-only routes under `/api/v1/admin/developers`:

- `GET /`
- `POST /`
- `PATCH /{user_id}/status`

Login and password-change responses include a server-selected `redirect_to`; the frontend does not infer authorization from editable client state.

### 5.3 Authorization dependencies

Define `get_current_user`, `require_customer`, `require_developer`, and `require_password_changed` dependencies. Authentication returns `401`; authenticated but unauthorized access returns `403`; required password change returns stable `409 password_change_required` for APIs and redirects pages to `/change-password/`.

All existing engineering APIs in `main.py` except health and authentication routes require developers. `/dashboard/` is developer-only. Support APIs require an authenticated active user and apply ownership filtering. Developers may use the support UI through developer-owned test conversations, but cannot impersonate a customer.

## 6. Frontend Structure

Create three small Chinese static applications:

- `/login/`: email/password form, validation, safe error state, links to customer registration.
- `/register/`: display name/email/password/confirmation, customer role fixed by the server.
- `/change-password/`: current password/new password/confirmation and first-login explanation.

The existing support app adds logout and current-user identity. The existing Dashboard adds current developer identity, logout, and a `开发人员管理` view consistent with its current navigation and visual system. It does not duplicate or hide the existing developer observation tools.

Frontend code never stores a session token in local storage. It relies on the HttpOnly cookie and treats `/api/v1/auth/me` as authoritative.

## 7. Error and Recovery Behavior

- Duplicate customer registration returns a stable conflict response without revealing password state.
- Disabled users receive a generic login failure and all their existing sessions are invalid.
- Expired/revoked sessions clear the browser cookie and redirect to login.
- A database transaction covers developer creation/status changes and associated audit events.
- The last active developer cannot be disabled.
- A developer cannot disable their own currently authenticated account.
- Failed authentication must not create a session or change `last_login_at`.
- Existing support confirmation/idempotency behavior is unchanged.

## 8. Testing Strategy

Tests are written before implementation and include:

1. Migration idempotency, seeded developer, foreign keys, indexes, and conversation-owner migration.
2. Password hashing, wrong-password behavior, password policy, and no plaintext persistence.
3. Registration, login, logout, expiry, revocation, forced password change, and restart persistence.
4. Customer/developer page redirects and API role enforcement.
5. Customer conversation ownership, cross-user denial, and unowned legacy isolation.
6. Developer creation, duplicate email, self-disable rejection, last-developer protection, and session revocation on disable.
7. Login, registration, password-change, support, and Dashboard static accessibility contracts.
8. Browser flows for customer registration/login/support and initial developer login/change-password/Dashboard/developer creation.
9. Full existing backend and saved-artifact quality gates.

## 9. Migration and Compatibility

SQLite migration execution becomes ordered rather than hardcoded to migration 1. Migration 2 must be idempotent through `schema_migrations`, preserve all existing data, and run automatically during normal startup.

Existing tests that construct application services directly may use an explicit authentication bypass dependency or authenticated test client. Product defaults never bypass authentication. Benchmark helpers remain in-memory and do not require web login.

## 10. Operational Configuration

Add:

- `ECOM_AUTH_SESSION_HOURS=12`
- `ECOM_AUTH_COOKIE_SECURE=false`

The initial administrator is fixed migration seed data as requested. README prominently requires changing its temporary password immediately. No environment variable or working secret is needed to create that account.

## 11. Acceptance Criteria

- An unauthenticated visitor sees the login page rather than support or engineering content.
- A newly registered customer logs in and reaches only their own support center conversations.
- The seeded initial developer is forced to change the temporary password, then reaches the existing complete observation Dashboard.
- A developer can create another developer from the Dashboard; the new developer must change their temporary password.
- Customers cannot access any Dashboard page or engineering API.
- Developers cannot access another customer's support conversation through customer APIs.
- Passwords and raw session tokens never appear in SQLite, API payloads, logs, or frontend storage.
- Authentication and support state survive API restart.
- The complete automated test suite and local validation gates pass.

## 12. Deferred Production Work

Enterprise SSO/OIDC, MFA, email verification and recovery, distributed rate limiting and lockout, CSRF tokens for cross-site deployment, tenant organizations, managed secrets, external identity stores, production HTTPS termination, and formal security review remain deferred.
